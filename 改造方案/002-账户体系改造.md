## 一、账户编号体系

### 格式

| 角色 | 编号格式 | 示例 | 说明 |
| --- | --- | --- | --- |
| 学生 | `S` + 两位年份 + `-` + 四位序号 | `S26-0001` | 学号 |
| 教师 | `T` + 两位年份 + `-` + 四位序号 | `T26-0001` | 教师号 |
| 家长 | `P` + 两位年份 + `-` + 四位序号 | `P26-0001` | 独立编号。**不派生自学号**——家长与学生是多对多，派生编号在多对多下不成立 |
| 管理员 | `A` + 两位年份 + `-` + 四位序号 | `A26-0001` | 补充设计，保持体系一致 |

年份用账号创建年份。序号在**该年份该角色内**递增，跨年重新从 0001 开始。

### 三条必须定死的规则（否则以后会出事）

1. **编号一经分配永不回收**。账号停用不删除、不释放编号。
   成因：编号会出现在历史答题记录、家长报告、支付流水里；回收后复用会让历史数据串号，
   而且**不会报任何错**。
2. **编号生成必须防并发重号**。用 DynamoDB 条件写（`attribute_not_exists`）占号，
   冲突则重试，**不能用「查最大值 +1」**——那个读的是已存在的记录，
   两个并发请求会拿到同一个号且都写成功。
3. **编号不是主键**。account 行主键仍是 Cognito `sub`；编号是带唯一索引的业务标识。
   成因：编号格式将来可能改（比如加校区前缀），主键改不得。

### 家长-学生：多对多关系

已定：**一个家长账号可关联多个学生，一个学生也可被多个家长关联**（父母两人各一个账号），
双向都可以发起关联。因此家长必须独立编号。

关系存 DynamoDB，**双向各写一条**，这样两个方向都能直接查、不用扫表：

```
PK: PARENT#<parent_id>   SK: CHILD#<student_id>    + status, created_at, created_by
PK: STUDENT#<student_id> SK: PARENT#<parent_id>    + status, created_at, created_by
```

### 🔴 关联必须经确认，否则是越权读取

**这是我要主动提出的安全点。** 如果家长能自己填一个学号就建立关联，
那他可以关联**任意**学生，从而看到别人孩子的学习记录、错题、报告——这是横向越权。

所以关联按发起方分两种路径：

| 发起方 | 是否需要确认 | 理由 |
| --- | --- | --- |
| **管理员分配** | 不需要，直接生效 | 管理员是可信方，且有审计留痕 |
| **用户自助发起**（家长填学号，或学生填家长号） | **必须对方确认** | 否则任意关联 = 任意读取他人数据 |

自助发起的关联进入 `pending` 状态，对方在自己的界面里看到待确认请求，
同意后才变 `active`。未确认的关联**不授予任何数据可见性**。

> 项目里已有 `parent_binding_status` 状态机（`pending_parent_profile` /
> `pending_parent_confirmation`），语义接近，可以复用其思路，但要改成以编号为准而非邮箱。

## 二、账户管理后台（admin）

### 列表页

- 按角色分组展示：学生 / 教师 / 家长 / 管理员，各自可见数量
- 筛选：角色、状态、创建时间区间、关键字（姓名 / 邮箱 / 编号）
- 每行：编号、姓名、邮箱、角色、状态、创建时间、最后登录时间
- 家长行额外显示绑定的学号；学生行额外显示绑定的家长

### 可执行的操作

| 操作 | 说明 |
| --- | --- |
| **分配账号** | 直接建号（不发邀请），生成编号 + 初始密码，管理员线下交付 |
| **发邀请** | 建号 + 发邀请链接，对方自己设密码激活 |
| 重发 / 撤销邀请 | 复用教师那套 `reissue_invitation` 的语义 |
| **重置密码** | 管理员强制改密（Cognito `admin_set_user_password`） |
| 停用 / 启用 | 状态切换，不删除 |
| 编辑资料 | 姓名、年级、学校、绑定关系 |

### 账号状态机（补充设计）

```
invited ──激活──> active ──停用──> suspended ──启用──> active
   │                                    │
   └──过期/撤销──> revoked               └──归档──> archived（只读，不可登录）
```

**不提供物理删除。** 成因同编号不回收：删掉账号会让历史学习记录、支付记录失去归属，
而且删除这个动作不可逆、不留痕。归档是可逆的。

### 审计日志（补充设计）

管理员对账号的每一次写操作都落一条审计记录：谁、什么时候、对谁、做了什么、改前改后。
成因：管理员能重置任何人的密码——**这个权限必须留痕**，否则出事时无法回溯。
项目里已有 `security_audit_repo.py` 可复用。

## 三、密码与改密

### 密码策略

维持现状（8 位 + 大小写 + 数字）。**可选**提到 10 位——对内账号由管理员分配，提高门槛的边际成本很低。

### 改密的三条路径

| 路径 | 谁发起 | 要验证什么 |
| --- | --- | --- |
| 自助改密 | 用户本人 | **必须输入旧密码**（Cognito `ChangePassword`，天然要求已登录 + 旧密码） |
| 管理员重置 | admin | 管理员身份 + 审计留痕；用户下次登录**强制改密** |
| 邀请激活时设密 | 被邀请人 | 邀请令牌有效 |

**没有第四条**——「忘记密码自助找回」按你的要求下线。

### 改密的二次验证：旧密码 + 邮箱验证码（已定）

流程：输入旧密码 → 向注册邮箱发验证码 → 输入验证码 + 新密码 → 完成。

**不引入手机号与短信**（瑞士短信约 $0.07/条，且要处理国际格式与送达失败）。SES 已在用，成本 $0。

验证码的设计要求（这些不写死就会写成漏洞）：

- 6 位数字，有效期 **10 分钟**
- **一次性**：用过即失效
- **限流**：同一账号每小时最多发 5 次，防止拿它当发信机器打爆别人邮箱
- **比较用常数时间**（`secrets.compare_digest`）
- **验证码错误的提示不能区分「码错了」和「码过期了」**——否则是枚举信号
- 验证码**不写进日志**

## 四、不做清单

| 不做什么 | 为什么 | 什么条件下重新评估 |
| --- | --- | --- |
| **不做忘记密码自助找回** | 需求方明确要求「只能改密不能找回」。代价：用户忘密只能找管理员 | 对 C 端开放，管理员重置成为支持负担 |
| **不新增手机号与短信验证** | 已定改密走邮箱验证码。现在完全没有手机号字段；瑞士短信约 $0.07/条，且要处理国际格式与送达失败 | 要上短信 MFA，或邮箱不可达成为实际问题 |
| **不做未成年／家长信息的强制校验** | 需求方明确取消——邀请制下账号由管理员分配，年龄与监护关系在线下已确认 | 恢复对 C 端自助注册 |
| **不换认证框架** | 见 001 否决记录 | 001 里列的 4 个恢复条件任一成立 |
| **不动授权层（208 条路由清单）** | 角色存在 DynamoDB，不在 Cognito。本卡只改「谁能开户」和「账号长什么样」 | 要把角色下放到 IdP |
| **不做物理删除账号** | 删除让历史记录失去归属且不可逆 | 出现法律要求的数据删除（GDPR 被遗忘权）——那时要做的是**匿名化**而非删除 |
| **不回收编号** | 复用会让历史数据串号且不报错 | 无。这条不应该被推翻 |
| **不做批量导入** | 当前规模手工够用 | 单次要开 20 个以上账号 |
| **不在本卡补前端 refresh 缺口** | 后端 `/auth/refresh` 早有，前端一行没调用，token 1 小时过期即掉线 | **建议单独立卡并优先做**——否则账号体系做完，用户照样一小时掉一次线 |
